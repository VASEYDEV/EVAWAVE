# 2026-09-26 — S4: Supabase library with RLS

S4 per SPEC §3. Setup is in `docs/runbooks/supabase.md`.

## How RLS is proven without a Supabase project

There is no Supabase project, and creating one would be an outward-facing step beyond the
brief. So the RLS test runs the real migration SQL in PGlite (Postgres compiled to WASM,
`@electric-sql/pglite`). Before relying on it, a probe confirmed that PGlite enforces RLS
for a non-superuser role under `SET ROLE`.

`tests/support/supabase-shim.sql` recreates what the migrations rely on from the platform:
- the `anon`, `authenticated` and `service_role` roles;
- `auth.users`;
- `auth.uid()`, reading the JWT subject the way Supabase's definition does;
- Supabase's default grants on new public tables.

The last one matters. The migration must revoke what it does not want, and a mutation
check shows the test notices when it does not.

## Evidence

- `tests/integration/library-rls.test.ts`: 43 passed. For each of the seven user-scoped
  tables, A reads its row (positive control). B:
  - cannot read it, either by key or by scanning;
  - cannot update it (0 rows, or permission denied on link tables, which have no update
    grant), with the row checked unchanged by a superuser;
  - cannot delete it (0 rows, the row still there);
  - cannot insert a row owned by A (RLS violation).

  B also cannot link A's profile or file even as the link's owner, and cannot move a row
  to A. Anon reaches no table, and genres are read-only. Files cannot claim
  `local_only = false`, `updated_at` is stamped on edit, and the columns match
  `LIBRARY_COLUMNS`.
- **Mutation checks.** Each of these fails the test:
  - RLS off on `tags` (9 failures);
  - a profile select policy of `using (true)`;
  - no ownership check on profile-genre links;
  - leaving `anon` its default privileges.

  Removing the `with check` from the tag update policy survives. That mutant is
  equivalent: Postgres reuses USING as the check.
- **e2e** (`tests/e2e/library.spec.ts`), without Supabase:
  - `/library` and `/login` say plainly that Supabase is not configured and pass the axe
    WCAG 2.2 AA scan;
  - `/auth/confirm` with `next=//evil.example` redirects to `/login`, not off-site;
  - site navigation works.
- `bash scripts/gate.sh` reports GATE: PASS.

## Decisions made while building

- **Sign-in.** It uses Supabase Auth email links, with the token-hash template and a
  server confirm route. That is managed auth with no passwords (CLAUDE.md §5). The
  library UI needs a session because every table is owner-scoped.
- **Links.** Link tables carry their own `owner_id`, and insert policies require the
  linked rows to belong to that owner. Without that check a user could attach their
  row to someone else's profile.
- **Least privilege.** The migration revokes Supabase's default grants and grants
  `authenticated` only what the policies allow. Link tables get no update grant.
- **Profiles.** A style profile saved from the library takes the composer's current
  spec in this browser, sliced to D1–D6, D8 and D9, with `provenance.kind: 'hand-built'`.
  Audio-analysis profiles arrive in S5.
- **The typed client** uses a `Database` type written from the migration. The RLS test's
  column check pins it until `supabase gen types` can run against a real project.
- **Dynamic rendering.** `/library` calls `connection()`, so the "not configured" check
  and the session run per request and are not baked into a static page at build time.

## Open

- The library has not been exercised against a live Supabase project, because none
