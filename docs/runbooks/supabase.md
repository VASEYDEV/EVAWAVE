# Runbook: Supabase for the library (S4)

The library (`/library`) needs a Supabase project. The composer works without one. Until a
project is configured, the library and sign-in pages say so and nothing else changes.

## 1. Create the project and apply the migrations

1. Create a Supabase project. Keep the service role key out of the repo and out of the
   client (`.env.example`, CLAUDE.md §5).
2. Apply `supabase/migrations/` in filename order. Either:
   - with the Supabase CLI: `supabase link --project-ref <ref>`, then `supabase db push`;
   - or paste each file into the SQL editor, oldest first.

   `20260926000000_library.sql` creates the tables with RLS on every one.
   `20260926000100_seed_genres.sql` loads the curated genres. It is generated by
   `node scripts/build-genre-seed.mjs` from `src/data/taxonomy/genres.json`, and running
   it again updates the records. `20260926000200_save_import.sql` adds
   `public.save_import`, which saves an audio import's file metadata and style profile
   in one transaction under RLS (security invoker; `authenticated` only) and returns the
   file id, the profile id and the owner the rows were written for.
   `20260926000300_file_record.sql` adds `public.file_record`, which says whether the
   caller has a file record for a hash and who the caller is (security invoker;
   `authenticated` only). `/library` uses it before removing a local copy.
   `20260926000400_songs.sql` adds songs and their immutable variants with RLS, and
   `public.freeze_variant`, which saves a song and freezes it as the next variant in one
   transaction when the song is still at the revision the caller read. It is the only way
   to create a variant, so it is security definer and checks that the song is the
   caller's itself (`authenticated` only). It takes the title, the spec and the parent; a
   variant's diff and coverage are derived by the app, never stored. `20260926000500_takes.sql` adds the take log: takes on the
   caller's own variants, with RLS and no edits.
3. Optional: regenerate the typed schema with
   `supabase gen types typescript --project-id <ref>`. Compare it with
   `src/lib/library/schema.ts`; the RLS test pins the column lists.

## 2. Environment

Set the public values in Vercel (or `.env.local`):

| Variable | Value |
| --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | the project URL |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | the anon (publishable) key |

Set both or neither. Setting only one makes `src/proxy.ts` throw by design.

## 3. Auth (email sign-in links)

EVAWAVE signs users in with Supabase Auth email links; there is no password flow.

1. **Authentication → URL configuration.** Set the Site URL to the deployment origin, and
   add `<origin>/auth/confirm` to the redirect URLs, including preview origins.
2. **Authentication → Email templates → Magic link.** Point the link at the confirm
   route, so the server can verify the token and set the session cookie:

   ```
   <a href="{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=email&next=/library">Sign in to EVAWAVE</a>
   ```

   `/auth/confirm` accepts only same-site `next` paths (`src/lib/auth/redirect.ts`).
3. Configure custom SMTP before real use. Supabase's default sender is heavily
   rate-limited and meant for testing.

Supabase Auth rate-limits sign-in emails and token verification per its project
settings. Those limits are the rate limit on the two public auth endpoints (CLAUDE.md §5).

## 4. Verify

- Sign in at `/login`. The link lands on `/library` signed in.
- Create a tag and a style profile (saved from the composer's current spec), then link a
  genre to the profile.
- Sign in as a second user in another browser. The first user's rows do not appear. The
  RLS test (`tests/integration/library-rls.test.ts`) proves the same against the
  migrations in CI.
